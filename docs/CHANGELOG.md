## [Unreleased]

### Added
- **`AGENTS.md` §3-bis, the verification rules.** Nine rules, each paid for by a defect that reached a commit or a VM in this session: verify the effect of an edit rather than its `ok`; no pipe between a command and `$?`; a check producing no result must say so; see a guard fail before trusting it; run it rather than read it; never state a cause you did not establish; scope a search before concluding an absence; never rewrite a file by line range; a counter nobody reads may as well not exist. They are in the working contract rather than in a habit, because a habit is not a rule.
- **`F2.WS.04`, the halves that build: the shipped policy file and the trie backend.** `deploy/policy/skeleton.aisme` is the policy an operator edits — three rules and the write scope — and it **compiles through the real compiler** in a test, so it is a policy rather than a document. `aisme-linux::BpfTrieBackend` lowers a `CompiledPolicy` into `BPF_MAP_TYPE_LPM_TRIE` keys with `prefix_len` in **bits**, carries each rule's enforced verdict, and **refuses a prefix longer than the key rather than truncating it**: a truncated key matches a shorter prefix, which is a broader rule than the one written, so the policy would silently become more permissive. Every rule is accounted for — accepted with the verdict this target enforces, or rejected by name (`F1.PL.08`).
- **`A-05` is checked on every L3 engine, not only `agentd`.** The rule says the composition root is the only module that names an adapter; the gate scanned one crate, so a second engine — `aisme-loaderd`, the one that holds `CAP_BPF` — could have scattered platform choices while the gate still said PASS. It now walks every L3 crate from `layers.toml`, each with its own `src/platform` root, proven by making `loaderd` name an adapter and watching the gate name the file and the adapter.
- **The slice is connected: `aisme-agentd --run` drives sensors → engine → the real WAL, and a declaration crosses the whole of it.** `WalSink` is the file-backed end of `aisme-core::wal`, whose record format, header and replayer already existed in L1; what was missing was the file, which is I/O and so belongs in L3. It fsyncs **per batch, not per event** — one fsync per tick, and the window a crash can lose is exactly one tick — rolls segments at `SEGMENT_BYTES` with each new segment carrying its own header and the `seq` it starts at, and writes nothing for an empty tick so an idle daemon does not fsync forever. A declaration reaches the engine as a **`Sensor`**, not through a private path: §3.2 has three interfaces and not fifteen subsystems, so the engine sees one stream, correlation matches within it, and the WAL records the claim beside the actions that would falsify it (`DT-04`). L0 gains `RawEvent::semantic_mut`, the counterpart of `file_path_mut`, so the one place that knows the layout is the one place that writes it. **Verified end to end on a real socket and a real file**: three `declareToolCall` calls answered `accepted`, and `aisme-core::wal::replay` read back three records with `kind=0x6003`, their ids and `tool_name="Bash"`. `slice_tests` is that run as a test, so the seams cannot come apart in silence. (`crates/aisme-agentd/src/{main,wal,declare}.rs`, `crates/aisme-ebpf-common/src/event.rs`)
- **`F2.WS.03` — `declareToolCall`, one new Annex I method, and the token that must never cross it.** The task said "emits" without naming a channel; the channel is the control-plane socket that already exists (`F1.IPC.01`) and already authenticates by peer identity, rather than a private side channel that would later have to be removed. `Method::DeclareToolCall` is `AnyAuthenticated` — an agent declares its own work — and **not idempotent**, because two identical declarations are two tool calls, not one retried. **It authorizes nothing**: no grant, no verdict, no scope, and a test asserts the response carries none of those words; `DT-04` exists precisely because a declaration may be a lie. Beyond `DECLARATIONS_PER_MINUTE` the answer is the *result* `rate_limited`, not an error (Annex I.2), and the bound is **derived rather than guessed**: the reference workload is 200 tool calls/hour (§2.19), so 64/minute leaves about nineteen times that in headroom while cutting a storm — which is cheap to send and expensive to correlate. `aisme-agentsim --declare <socket>` sends one declaration per `toolcall` entry as it replays. **The correlation token never travels on it**, and the test that says so now watches all three streams; a second test parses the emitted line with the server's own parser, so the hand-written request and the codec cannot drift apart in silence. (`crates/aisme-proto/src/rpc.rs`, `crates/aisme-agentd/src/ipc.rs`, `crates/aisme-agentsim/src/replay.rs`, plan Annex I.1)
- **`F2.WS.02`, first half — the hot loop gains its canonicalization stage.** `aisme-core::resolve::PathResolver` is an L1 **ingest hook**, deliberately not one of the three §3.2 traits and so not part of the GATE F1 freeze: canonicalizing a path is I/O and `A-01` keeps I/O out of L1, so the loop knows only that *something* resolves. `Engine::tick` takes `&mut dyn PathResolver` and runs the stage before anything reads a path; it is **the only stage that may clear `FLAG_PATH_UNRESOLVED`**, and it clears it only when it resolved something. `TickReport` gains `resolved`/`unresolved`, because a path nobody could canonicalize is a fact about the machine and a silent zero would hide a resolver that stopped working. L0 gains `RawEvent::file_path_mut`, the one way to edit a path in place — layout work, so the `unsafe` lives where §3.1 permits it. On Linux, `RealpathResolver` asks the kernel with `open(O_PATH)` + `readlink("/proc/self/fd/N")` into fixed buffers: `std::fs::canonicalize` is shorter and allocates a `PathBuf` per call, which is one allocation per event on the hot path and `I-22` allows none. Its LRU is bounded and its evictions counted, sized by a named constructor (`for_sessions()`, 1024 entries) exactly as `Interner::for_paths()` is. `NullResolver` reports every path unresolved — true — so the no-kernel path measures the same code. **Measured with the new stage inside the region: 200 064 events over 1 563 ticks, 0 allocations, 0 drops.** The daemon now reports `canonicalization: available` by asking, not asserting. (`crates/aisme-core/src/resolve.rs`, `crates/aisme-linux/src/resolve.rs`, `crates/aisme-agentd/src/platform/mod.rs`)
- **`cargo xtask vm run --with-dist` — point 12's transport, and the first kernel verdict on the F2 program.** Committed under **`F2.WS.10`** as the nearest existing task: the transport is a GATE F2 prerequisite that point 12 specifies and no task row owns, and task IDs are append-only (`I-23`), so it is recorded here rather than given an invented ID. Builds the six product binaries statically, stages them into the seed ISO under `/opt/aisme/` with a `sha256` manifest, and installs them in the guest **re-hashing every one**; a mismatch prints both hashes and stops the command. `xtask` is excluded — it is the host's build tool, not something AISME installs. **The transport constraint point 12 did not see:** this host's glibc is 2.43 and every guest's is older (2.31 on Ubuntu 20.04 and Debian 11), and glibc symbol versioning is forward-only, so a dynamically linked binary built here runs on **no** image in the matrix. `-C target-feature=+crt-static` on the gnu target solves it with nothing to install — measured: static-pie, no glibc version references, `aisme-agentd` at 2.15 MB against §2.22's 12 MB ceiling — where musl would have cost `rustup target add` plus `musl-tools` by sudo. With it, `agentd --load-sensor` (in the composition root, where naming an adapter is legal) gets the verdict `bpftool` structurally cannot give: **6.8 `ACCEPTED`** with `ringbuf: true` and `health: Healthy`, **5.4 `REFUSED`** naming the kernel, `BPF_MAP_TYPE_RINGBUF` and the failing map. Prediction held on both, and the risk written down beforehand — a 320-byte `RawEvent::ZERO` against a 512-byte BPF stack — did not materialise. (`xtask/src/vm.rs`, `crates/aisme-agentd/src/platform/mod.rs`, plan GATE F2's four `vm run` lines)
- **`F2.WS.01` — `BpfSensor`, one tracepoint, a real ring buffer.** The first F2 code. `crates/aisme-ebpf` gains the `sys_enter_openat` tracepoint: session filter as one kernel-side hash lookup on `tgid` (filtering in user space would move the whole `openat` firehose across the ring boundary to be discarded), `bpf_ringbuf_reserve` of a `RawEvent`, path copied from the caller's pointer with `bpf_probe_read_user_str`, per-CPU `seq` and a per-CPU drop counter for `F2.WS.02`'s `DropNotice`. `aisme-linux` gains `BpfSensor` and its first dependency, `aya =0.14.0`, pinned exactly because `F0.VER.01` validated the MSRV against that version. `aisme-agentd::platform` names it behind `cfg(target_os = "linux")` — the only module allowed to (`A-05`) — gated on `caps.ringbuf`, which keeps `I-12` intact: `probe()` claims nothing until `F3.LD.01`, so the host test suite attempts no BPF load, and a test pins that. New wire flag **`FLAG_PATH_UNRESOLVED`** (bit 1, additive — a flag consumes a bit, never an offset, §3.6): a tracepoint sees the caller's string, not the kernel's resolution, and nothing may decide from a path carrying it (`I-28`). **`ppid` is left 0 in the kernel and the comment says why** — a parent's tgid needs CO-RE against a vmlinux BTF that F2 does not load; ingest fills it (`F2.WS.02`), and 0 is unambiguous because tgid 0 is `swapper`. **Loading is the ring-buffer feature test**: a kernel without `BPF_MAP_TYPE_RINGBUF` refuses the map, and `start` returns `Unsupported` naming the kernel and the map type. No perf-buffer fallback — that is `F3.PT.*`, and shipping a second untested transport inside a risk-removal phase would add the risk the phase exists to remove.
- **`ADR-08` — the F1 freeze binds trait signatures; `#[non_exhaustive]` data types grow additively.** Raised by the first post-freeze change, which is not a trait: `Sensor::capabilities` keeps its signature and `CapabilitySet` gains a field. Frozen and ADR-gated: a trait's method set, any signature, and the *meaning* of a field. Permitted additively: a new field on a `#[non_exhaustive]` struct whose zero value means "not measured", landing with its doc comment, its `NONE` value, a test pinning what the absence means, and an update to whatever derives a decision from it. The alternative was measured, not argued: making honesty expensive is what left one field carrying two capabilities and reporting a tier the machine could not deliver.
- **`I-28`** in `docs/ai/invariants.md` — a decision that permits a path-bearing syscall is delivered as a validated descriptor (`SECCOMP_IOCTL_NOTIF_ADDFD`), never as permission to re-resolve the path; where `ADDFD` is absent the escalate class is denied, and the tier says so. Answered as `Q-13` on 2026-09-07 and cited by the plan and by `tier_of`; it now lives in the registry `CLAUDE.md` sends the reader to, not only in a changelog line.
- **`verify-docs` enforces the rule this file states.** Every task ID in a commit subject must have a changelog line; the check reads the whole history, expands the `verify(F0.VER.03,.06,.08)` shorthand so a sibling run is not read as six absences, and fails the gate. It found seven missing lines on its first run — the rule had been written at the top of this file since F0 and nothing implemented it. (`xtask/src/docgate.rs`)

### Fixed
- **A loader error blamed a cause it had not measured.** `BpfSensor::start` reported every load failure as "BPF_MAP_TYPE_RINGBUF needs 5.8", so a missing-BTF parse error on a 6.8 kernel arrived dressed as a ring-buffer problem. It now reports the loader's own words and adds the ring-buffer cause only when the error is about creating a map.
- **Two defects found by running the slice rather than reading it.** The hot loop had no pacing: nothing in it blocks, so it spun a core flat out and finished 8 000 ticks in milliseconds — burning the §2.22 CPU budget on nothing and draining no more events for having tried. An idle tick now sleeps what it did not spend; a busy one does not sleep at all, so throughput under load is unaffected. And `DeclarationSensor` counted refused declarations into a field nobody read. It is reported through `health()`, which the engine already polls, naming what the refusal costs — correlation has no ground truth for those tool calls, so their actions look unexplained. A counter nobody reads may as well not exist.
- **Fourteen `file:line` citations in `docs/05` pointed at the wrong line, and the class is now mechanical.** Seven had drifted when the plan grew — the `seccomp_addfd` field block, the Annex D.1 rows and `--with-dist` all added lines above them — and the rest had been written approximately and never checked, so the task-row citations for `F2.WS.03` through `F2.WS.11` each named the row *above* the one they meant. A `file:line` citation is what this project accepts in place of an unverified claim, so fourteen that do not resolve are fourteen unverified claims wearing the clothes of verified ones. All corrected against the plan's current content, and `verify-docs` now **fails** when a ``` `<task-id>` row (`:N`) ``` citation names a line that does not contain that task ID — proven by breaking one deliberately and watching the gate name it. The first version of the check had a bug of its own: a 12-character lookahead truncated `1620` to `162`, so every citation "failed" for a fake reason; a check that is wrong about a real defect is still wrong.
- **Three defects in the staging code, all found by running it rather than reading it, and one the layering gate caught.** The guard printed *"refusing to run: a staged binary does not match the manifest"* and then **ran the command anyway** — a mismatch that looks handled is worse than no check; the command now sits inside `if [ "$BAD" = 0 ]` and a mismatch exits non-zero. `cp /opt/aisme/aisme-*` silently missed two binaries because the CLI is called `aisme` with no hyphen; the hash check surfaced it as `guest=missing`, and copying is by explicit name now. A slice-based rewrite of `xtask/src/vm.rs` **deleted 716 lines**; `cargo build` found it at once, the file was restored from git and every change re-applied by anchor with `grep` verification — which is what project rule 1 exists to prevent. And `verify-layering` failed on `A-05`: the `--load-sensor` diagnostic named `aisme_linux::BpfSensor` from `main.rs`, outside the composition root; it moved to `platform/`, which is also where it belongs by meaning. The first three left tests that did not exist — the generated prologue is parsed by a real `sh -n`, and two tests **execute** the script, one asserting a bad hash stops the command and one asserting a good hash lets it run.
- **`vm probe` gains the two `F2.WS.01` rows, and three versions of one of them measured nothing while printing `PASS`.** The tracepoint-offset row reads `sys_enter_openat`'s argument offsets from the guest's own format file, because they are an ABI of a *format file* rather than of a header the build can check. Measured on 5.4 and 6.8: `filename 24`, `flags 32`, `mode 40` — all `MATCHES`, prediction held. Getting there took three tries that all looked identical from outside: a `printf` newline escape a layer turned into a real line break, then field indices off by one (`$3`/`$5` for `$2`/`$4`) so `awk` matched nothing, printed nothing and **raised no error**. The row now does the comparison itself and prints `NONE FOUND` when it parses nothing. The second row reports what `bpftool` can say about the product object and says plainly what it cannot: **the verifier's verdict is owed**, because libbpf refuses an aya object over the container — bare `tracepoint` section name on 5.4, legacy `maps` section on 6.8 — while aya parses both (`aya-obj` `obj.rs:327`, `obj.rs:1073`). A prediction of mine fell there: I expected `ACCEPTED` on 6.8.
- **`I-27`'s gate did not enforce `I-27`.** The check demanded that a workflow contain `"on:"`, `"push:"`, `"pull_request:"` **and** `"schedule:"` — all four — before flagging it, so the single most expensive file, one carrying only `on: push:`, passed clean; a `workflow_dispatch` workflow, which bills when the button is pressed, passed too. And since the repository has no `.github` at all, the function returned `true` on its first line and had **never run against anything**. The rule is zero hosted-CI cost, so the check is now over **existence**: any file under `.github/workflows/`, and any `action.yml`/`action.yaml` anywhere, fails the gate whatever its content. Five unit tests exercise it on synthetic listings — including the push-only case that used to pass and the free files (`CODEOWNERS`, issue templates) that must keep passing — and it was proven end to end by creating that exact workflow, watching `verify-docs` exit 1, and removing it. (`xtask/src/verify.rs`; wording aligned in `CLAUDE.md`, `docs/ai/invariants.md`, `docs/ai/AGENTS.md`)
- **Second coherence pass, over the state the first one left.** The 5.4 tier change had not reached six places that still called it `L2-` or still stated the L2- rule as `seccomp_unotify`: the `F0.VM.02` plan row (which contradicted itself inside one cell), Annex D.1's **L1** row (whose condition was "no BTF/CO-RE" — and 20.04 ships BTF and is L1), the `distro-default-lsm-lists` memory table and its two closing paragraphs, and two `STATE.md` Done rows. Also: `## Blocked` listed two blockers and then said "Nothing" four paragraphs later, so a reader stopping at the heading saw live blockers that were resolved; `Q-13` sat under "Open decisions needing an ADR" after being answered; and `ADR-03` had no forward pointer to the `ADR-08` that scopes its freeze. All corrected, with the reasoning of every paragraph kept.
- **`F0.VM.02` re-measured, and one tier moves: Ubuntu 20.04's 5.4 is `L1`.** `Q-13`'s answer split the capability `seccomp_unotify` was carrying. Trapping a syscall (the notifier, kernel ≥ 5.0) and *answering* one with a validated descriptor (`SECCOMP_IOCTL_NOTIF_ADDFD`, ≥ 5.9) are two capabilities, and L2- promises the second. `CapabilitySet` gains `seccomp_addfd`, `tier_of` reads it, `degradations` names what its absence costs, and a test pins that the notifier without `ADDFD` is `L1`. The probe feature-tests the ioctl rather than the kernel version — `NULL` argument on a live listener, then `errno`. **Prediction written first; it held on all seven images**: 5.4 answers `EINVAL` (22) and has no `ADDFD`; 5.10, 5.15, 6.1, 6.8 ×2 and 7.0 answer `EFAULT` (14) and keep their tier. Matrix: **L1**, L2-, L2, L3, L2, L3, L2. The first version of the discriminator read "absent if `ENOTTY`" and reported "present" everywhere — the seccomp notify fd is an anon inode whose handler answers an unknown command `EINVAL` from its `default:` arm, so `ENOTTY` is unreachable; §2 of point 13 had written the right rule and the code diverged from it. (`crates/aisme-core/src/{capability,tier}.rs`, `xtask/src/vm.rs`, `docs/05_challenge_ampliacion_f2.md` point 13, `docs/reports/01_f0-verification.md`)
- **`vm probe --all` printed `PASS` without ever comparing the tier it measured with the tier the plan expects.** The `result` column came from the guest's exit code alone and `Image.expect` was free text nothing parsed, so the summary could not disagree with the plan — and the earlier claim that seven of seven passed "with every measured tier equal to the plan's expectation" was true by coincidence, not by check. It surfaced the moment a row actually moved: `L1` sat beside `plan expects 5.4 (L2-)` under a green `PASS`. `Image` now carries the expected tiers machine-readably, `result` is the conjunction of "the probe ran" and "the tier is one the plan names", a disagreement prints `FAIL tier` and lifts the exit code, and a unit test pins the printed text and the compared list to agree. The defect biased **optimistic**, which is the urgent direction. (`xtask/src/vm.rs`)
- **`F0.VER.03`, `F0.VER.06`, `F0.VER.08`, `F0.VER.09`, `F0.VER.10`, `F0.VER.11`, `F0.VER.17`** — the seven verification rows of commit `0616e0e` ("seven rows against primary sources; two plan corrections"), recorded in `docs/reports/01_f0-verification.md` and in §F0.4 but never given a line here. This is the gap the check above exists to close, and the reason it is not merely a warning.
