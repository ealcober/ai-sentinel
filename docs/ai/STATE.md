## Blocked

**The ptrace blocker is closed** (`ADR-09`). `aisme run` forks the supervised command and stays as
its parent, so Yama permits reading every descendant at any depth with **no grant at all** and no
component holds a capability. Measured: `sh -c 'cat /etc/hostname'` goes from 2 delivered and 13
denied — every denial the grandchild's, every one *"the path argument could not be read"* — to 6
delivered and 0 denied, and three shells deep to 10 delivered and 0 denied. `PR_SET_PTRACER` is gone
from the session path. **What is owed is re-running GATE F2's five enforcement lines against the
shipped configuration**, which is now what they measure.

**`F2.WS.04`'s double buffer cannot use BTF maps at the pinned toolchain — and the second-object fallback is refuted, not pending.** A standalone object carrying **only** `.maps`, no programs and nothing to mix with, fails identically: `BTF error: unexpected BTF type id 45`, which is `aya-obj 0.3.0`'s resolver following a type reference into something it does not expect (`btf/btf.rs:104`). The obstruction is the BTF `bpf-linker 0.11` emits against what this aya reads; mixing sections was a consequence, not the cause. Measured on 6.8 and 5.4 in the same boot in which `--load-sensor` stayed `ACCEPTED`, so nothing regressed this time. **What replaces it**: two `LpmTrie` maps in the legacy `maps` section — the style proven to load on every matrix kernel — plus an `Array<u64, 2>` of `[generation, active_index]`. The cost is the single-word swap: a reader takes two lookups instead of one and needs its own no-torn-read argument. `docs/06_challenge_ampliacion_policy_object.md` point 1 carries the measurement; points 2–6 are being written against this mechanism. The alternative — moving the aya or bpf-linker pin — is the owner's, not a step inside `F2.WS.04`.

**Superseded (kept for the record):** `BPF_MAP_TYPE_ARRAY_OF_MAPS` exists in `aya-ebpf 0.2.1` only as a **BTF map** (`#[btf_map]`, `.maps` section), while the `F2.WS.01` program's maps are `#[map]` (legacy `maps` section). One object carries both sections — `readelf` confirms it — and **it does not load**: `no BTF parsed for object` by default, no `.BTF` section from `[profile.release] debug = 2`, and `BTF error` once `-C link-arg=--btf` emits four BTF sections. Measured on 6.8 and 5.4; 6.8 had been `ACCEPTED` before, so the attempt **regressed a verified program**, and the object was returned to its verified state and re-measured (`ACCEPTED`, `ringbuf: true`) before anything else was written.

**What unblocks it:** the policy maps in a **second BPF object** that `aisme-loaderd` creates and owns, which keeps the sensor's verified program untouched and puts the maps where `F3.PT.02` reads them anyway. The compile and lowering halves are done and tested; what waits is the publication.

**BLOCKING `F0.ASSET.02`: a declaration cannot be joined to an action made by its sibling.** The
daemon serving connections concurrently made both planes land in one session — measured, 5 of 5
declarations and 55 actions — and the trace still reports **55 unattributed**, because
`record::attribute` walks the action's **ancestry** looking for a declaration made by an ancestor.
In the topology a real agent has, the hook and the tool are two **children** of the agent: siblings,
never ancestors. The declaration also carries `ppid = 0`, so even the chain that would let them meet
is not recorded.

**What unblocks it** is a decision about what a declaration binds to, amplified against the source in
`docs/16` point 1 — and **the first proposal was refuted there**. Accepting a declaration whose
`tgid` *or* `ppid` is an ancestor, and breaking a tie by taking the latest, reintroduces exactly the
defect `actions_are_attributed_by_ancestry_and_not_by_arrival_order` (`record.rs:425`) exists to
prevent: every hook of a session has the agent as its parent, so all of them match at once. `docs/12`
M3 measures **14.4 %** of model turns issuing parallel tool calls, so about one turn in seven would
have its actions handed to the wrong declaration **while every total still came out right**. It also
widens who may explain an action from *an ancestor* to *any child of an ancestor*, which in an agent
session is every tool subprocess — an alibi surface, against `DT-04`'s premise that a declaration may
be a lie.

**What replaces it:** the same candidate rule, with the tie **reported instead of broken**.
`attribute` yields *attributed*, *unexplained*, or **ambiguous**; the declaration carries its parent
(read by the daemon from the connected peer, derived rather than claimed); and `Recorded` counts the
ambiguous separately. The 85.6 % of turns with one tool call in flight attribute exactly, and the
rest are marked rather than guessed — which is the principle `record.rs:34-40` already states: *"an
unattributed action is visible, while a wrongly attributed one is not."*

**Still the owner's**, and it is now one narrow question: whether `F0.ASSET.02` may be a fixture that
states an ambiguous fraction rather than explaining every action.

**Nothing else is blocked.** `F2.WS.01`'s verifier clause was the open one and is now closed: `vm run --with-dist` stages the product's own loader into the guest, and the kernel answered — `ACCEPTED` on 6.8, `REFUSED` on 5.4 naming `BPF_MAP_TYPE_RINGBUF`. The two items below were blockers, are not now, and keep their reasoning because both recur.

**`F0.GATE.01`'s hook is enabled** (2026-09-09, `git config core.hooksPath .githooks`). Every commit runs `gate --level commit`, which is why it is enabled rather than merely available: the owner's rule is that a `FAIL` is fixed before committing and never declared in a commit body, and a guard nobody runs is decoration. Bypass for a genuine emergency is `git commit --no-verify`, and using it is worth saying out loud.

**WSL interop is gone from this distribution** (`F0.WSL.02`): `cmd.exe` and `wsl.exe` fail with `exec format error` because `/proc/sys/fs/binfmt_misc/` no longer holds the `WSLInterop` entry. **Cause, half verified**: binfmt_misc is one kernel-wide table, and a guest's *termination* clears it for every distribution — four losses here. Three followed the systemd guest stopping, as [rancher-desktop#10049](https://github.com/rancher-sandbox/rancher-desktop/issues/10049) describes (masking `systemd-binfmt.service` does not help). The fourth and fifth followed a **first-time probe** in a non-systemd guest — the fifth with that guest still running and every other guest either held open or already stopped with the table intact — while the splitting run showed that neither an idle termination nor the probe script plus an explicit terminate clears it on a repeat run. The replay settled it (report, *WSL2 images*): `apt` is falsified; losses 1, 4 and 5 are the **first boot of a freshly imported guest with its `wsl.conf` applied** — a trivial session with no script loses the entry three seconds later, and every later boot of that guest is harmless — while 2 and 3 are the systemd guest's `ExecStop --unregister` chain and termination. What WSL's `init` does on that first boot stays unexplained, inside WSL 2.7.8.0. **What unblocks it**, the owner's action, either one:

```bash
sudo sh -c 'echo ":WSLInterop:M::MZ::/init:PF" > /proc/sys/fs/binfmt_misc/register'
```

or a new session in this distribution opened from Windows. A third option, the owner's to take: a sudoers line for that one command (`<user> ALL=(root) NOPASSWD: /bin/sh -c echo \:WSLInterop\:M\:\:MZ\:\:/init\:PF > /proc/sys/fs/binfmt_misc/register`) would let `vm` re-register after every guest run instead of the owner doing it by hand each time. **What holds so far**: `vm probe wsl2-<systemd variant>` keeps the guest open with a detached `sleep infinity` session and the entry survived that probe; both guests are currently registered, the systemd one held open (`ps` shows `wsl.exe -d aisme-wsl2-ubuntu-24.04 -- sleep infinity`). **What `vm up wsl2-*` now does**: it takes that first boot itself, waits five seconds, and re-registers the entry with `sudo -n` — or prints the line above and fails, so no later step inherits a dead interop; `vm probe` checks the same after every guest run. The sudoers line is what makes it hands-off. Prediction for the next `vm up` of a fresh import: the entry goes at its first boot and `vm up` says so; every `vm probe` after it leaves it alone.

**Host state, checked 2026-09-07.** `doctor` reports 15 of 15 (`/dev/kvm` back in group `kvm` after the owner's `chgrp`; after a WSL restart check it again — the node can come up in group `sgx`), interop is registered, and GATE F0 passed in full.

## Notes for whoever picks this up

**Start at `docs/ai/handoff/02_f2-walking-skeleton.md`.** It is the mid-flight handoff for F2, written at commit `34ba389`: what to read and in what order, the rules that were paid for by defects rather than chosen, the measured state of all eleven `F2.WS.*` tasks, the one unimplemented half and its cause, the next four steps in order, and the four decisions waiting for the owner.


- **Read Plan §3.1–3.2 before writing any code.** The layering rules (`A-01`…`A-06`) and the trait catalogue are the architecture. `aisme-core` must never learn what OS it is on — that single rule is what makes one engine serve Linux, WSL2, Android, iOS and the SDK.
- **F2 is a walking skeleton, not a feature phase.** Its out-of-scope list is as binding as its task list. If it grows features it becomes F3 with extra steps and the whole risk-transfer benefit is lost.
- **Plan Part II is the most valuable artefact here.** It exists specifically to stop the research's rejected designs from being re-implemented by a well-meaning contributor. Read it before writing kernel code. The precedence rule is in Plan §7.6.
- **Windows is served by WSL2** (ADR-02). The native driver spec lives in **Annex F** marked `[POST]` — do not implement it. Keep the `Sensor`/`Enforcer`/`Adjudicator` trait boundaries (§3.2); they are what makes that decision cheaply reversible.
- **The hardest unsolved problems**, both with documented fallbacks so neither can block the MVP: prompt delivery on headless/GUI Linux (`docs/design/01_permission-model.md` §7.3) and F4 tier-D offset resolution on stripped BoringSSL.
- **The benign corpus (§4.8.2) matters as much as the red team corpus.** A product that blocks `npm ci` is dead on arrival. Milestone M5 is the real go/no-go for exactly this reason.
- The permission model note is `SPEC` (`docs/design/01_permission-model.md`) and carries the `warn` verdict and suppression rules. F1, F7 and F8 implement it.
- **Two primitives make tier L2 real**: Landlock (in-kernel file deny) and `BPF_CGROUP_INET*_CONNECT` (in-kernel network deny). Both work without a reboot and without BPF-LSM, which matters because WSL2 — the Windows strategy — is L2 by default. **Landlock is confirmed on WSL2** (`F0.WSL.01`: ABI 7, `EACCES` outside the allowed path under a real ruleset); the matrix kernels are `F0.VM.02`, and the cgroup hook still needs a loader (`F0.VER.16`).
- **Every gate runs locally** (`I-27`). Do not propose GitHub Actions, self-hosted runners or scheduled cloud jobs. `.github/` does not exist and `verify-docs` fails if a push-triggered workflow appears.
- **The report's R1 register is the F0 verification backlog**, and its outcomes live in `docs/reports/01_f0-verification.md`. Sixteen live rows are still unmeasured (`R1-01`…`R1-18` less the withdrawn `R1-15`, plus `F0.VER.19`…`21`); four of them decide how a row reads (`R1-04` Landlock, `R1-16` cgroup hooks, `R1-18` no TPM under WSL2, `R1-12` hardware curves). The register must be empty at GATE F0.
