> Plan §F0.4 defines twenty-one rows. `F0.VER.15` is `DEPRECATED` (its claim `R1-15` was withdrawn under `I-27`), leaving **twenty live rows**. `cargo xtask verify-backlog` reads this file and fails while any live row has an empty `Outcome`. That is the correct state until GATE F0.

## WSL2 images (`F0.WSL.02`)

`cargo xtask vm up wsl2-ubuntu-24.04`, 2026-09-06: **imports and boots** (`PASS vm up wsl2-ubuntu-24.04: aisme-wsl2-ubuntu-24.04 imported, systemd=true`). Ubuntu's official WSL rootfs tarball, `wsl.exe --import` through interop, VHDX on NTFS under `%LOCALAPPDATA%\aisme\vm`, `/etc/wsl.conf` written and the distribution terminated so `[boot] systemd=true` applies. Its first `vm probe` run then measured four defects of the probe itself, each folded into `xtask/src/vm.rs`:

1. **securityfs is unmounted**, so the tier rule read `lsm: unreadable` as "no LSM" and printed **L2-** for a kernel with Landlock ABI 7 — the exact absence-as-value `F0.WSL.01` warned about, reproduced by my own probe. The tier probe now mounts securityfs and, failing that, reads `CONFIG_LSM`.
2. **An inline script does not survive `wsl.exe`**: Windows argument re-quoting turned awk's `\|` into a "backslash not last character" error and delivered `2>&1` as a bare `2`. The script now runs from a file on NTFS.
3. **Another distribution sees only `/mnt/c`**: `cp` of `probe.o` from this distribution's path failed with `cannot stat`. The object is staged on NTFS.
4. **`linux-tools-$(uname -r)` does not exist for the Microsoft kernel**, so `bpftool: command not found`. The installer falls back to the versioned binary of `linux-tools-generic`. The product-side reading is already the design: `loaderd` loads through `aya`, never through `bpftool`.

**Interop was lost twice, and the second time with a timestamp.** After the first import this distribution's `WSLInterop` entry vanished from `binfmt_misc` (`exec format error` on every `.exe`). So `vm probe wsl2-*` holds a systemd guest open for the session and names the terminate that will cost interop. The `nosystemd` variant and the cgroup axis remain unmeasured, and the WSL2 rows stay out of the matrix table above until each is.

## What these outcomes decide

0. **`F0.VER.16` and `F0.VER.19` were never toolchain-blocked; they are VM-bound.** Both exercise the verifier, which means loading a BPF program. This host reports `unprivileged_bpf_disabled = 2` and the shell holds no capabilities, so a load needs privileges — and `I-12` forbids a kernel-touching test on a host OS even where it would succeed. Recording them as "blocked on the toolchain" was wrong, and installing the toolchain is what exposed it.

1. **`F0.VM.*` does not need `virtme-ng` or a kernel build, and one of my own conclusions fell.** Under WSL2 there is no `/boot/vmlinuz` and a distro kernel panics under `virtme-ng` because 9p/virtiofs are modules there — both measured, both still true. From that I concluded the matrix needed kernels built per version. **That was wrong**: a distribution *cloud image* boots its own kernel and its own initramfs under plain `qemu`, no host rootfs mounted, no `sudo`, and the distro kernels are the matrix — 20.04→5.4, Debian 11→5.10, 22.04→5.15, Debian 12→6.1, 24.04→6.8, 26.04→7.0. `cargo xtask vm up/run/probe` implement exactly that: base image fetched once, a fresh qcow2 overlay per run (a restore from snapshot, which is what `I-12` asks for), a NoCloud seed carrying the commands. Ubuntu 24.04 is measured: it boots under KVM, reports **L2** (Landlock ABI 4, `CONFIG_BPF_LSM=y` compiled, `bpf` absent from the active list, BTF present, cgroup v2), matching the `6.8 (L2/L3)` row, and carried both BPF probes.

2. **The toolchain pin has a second half nobody had written down: LLVM.** `F0.REPO.02` set out to pin a nightly and record the Aya version it was validated against, and the first build failed with `ERROR llvm: Unknown attribute kind (105) (Producer: 'LLVM23.1.1-rust-1.100.0-nightly' Reader: 'LLVM 21.1.8')`. `bpf-linker` links the bitcode `rustc` emits, so **their LLVM majors must be equal**, and they are chosen in two different places by two different people. Measured on this host: `nightly-2026-01-01` → LLVM 21.1.8 (matches the installed `bpf-linker`), `nightly-2026-02-01`…`nightly-2026-06-01` → LLVM 22, current `nightly` → LLVM 23.1.1, stable `1.97.1` → LLVM 22.1.6, and apt tops out at `llvm-22-dev`. The pin is therefore `nightly-2026-01-01`, deliberately old, and `cargo xtask doctor` now compares the two majors so the next person sees it in five seconds instead of at link time.

3. **A prediction of mine fell, and the reason is worth more than the number.** Before measuring `F0.VER.13` I predicted 1–3× rather than the plan's 5–10×, reasoning that BLAKE3's advantage comes from SIMD parallelism over long inputs and that 320 bytes is too small to collect it. The measurement is 6.41×, inside the plan's range. The input size was not the variable that mattered: **SHA-NI was.** This CPU has none, so `sha2` runs a software SHA-256 at 160 MB/s; on a CPU with the extension it would be several times faster and the ratio would largely close. The lesson is that a hash benchmark without naming the target's crypto extensions is not a measurement of the algorithms, and the plan now says so where it chooses BLAKE3.

1. **Landlock cannot see UDP, so it cannot see QUIC.** `F0.VER.20` measured that `handled_access_net` has only TCP bind and connect bits and refuses anything else with `EINVAL`, and a UDP connect under a restricting ruleset went through untouched. This is not a gap in the design — the L2 network deny was always the cgroup `connect` hook — but it does mean Landlock is a **file** primitive with a narrow TCP addendum, and Annex B §B.9 now says so rather than implying address matching it does not have.

4. **`F0.VER.01` is why this register exists.** The claim was written when Aya was not yet pinned, and it is wrong by five minor versions. The failure surfaced the moment a real dependency was fetched, not through review. The root toolchain is now `1.97.1` and the MSRV `1.87`, the floor Aya sets; the workspace compiles and passes `clippy -D warnings` unchanged under it. **The lesson worth keeping: checking that a pinned toolchain is installed is not checking that it is adequate.** The previous commit verified the first and reported the file's claim as true; only fetching Aya's manifest tested the second.

3. **Tier L2 is real on WSL2, and proven rather than assumed.** `F0.VER.04` was `[BLOCKING]` because the L2 tier row, `F3.3`, `F2.WS.11` and risk `R-15` all rest on Landlock actually denying. It does: a write outside the allowed path returned `EACCES` under a real ruleset. `R-15` does not apply to WSL2.
4. **WSL2 can reach L3 with a configuration change, not a kernel rebuild.** Plan §2.16.1 left this conditional open and asked F0 to settle it. `CONFIG_BPF_LSM=y` **is** compiled into the stock kernel, and `CONFIG_LSM` is `landlock,lockdown,yama,loadpin,safesetid,integrity,selinux,apparmor,tomoyo` — `bpf` is **not** in the active list. So WSL2 is **L2 by default**, exactly as the plan says, and reaching L3 needs only `kernelCommandLine=` in `.wslconfig` plus `wsl --shutdown`. The custom-bzImage fallback the plan held in reserve is not needed on this kernel.
5. **Forensics on WSL2 are software-signed, by construction.** `F0.VER.18` holds with no TPM driver at all, so `R-18` stands and external anchoring is the default there (`I-18`).
6. **The toolchain, not the kernel, is what blocks the remaining blocking row.** `F0.VER.16` has every kernel prerequisite and no loader. It unblocks with `F0.REPO.06`.
7. **`cat /sys/kernel/security/lsm` is the wrong probe on this platform.** securityfs is not mounted on stock WSL2, so the file does not exist and a literal reading returns "no LSM list" — an absence read as a value, which general rule 9 forbids. `/proc/config.gz` and the Landlock syscall are the reliable probes, and §F0.4's command column says so.
